# INS native module + DB parity review (2026-09-09)

Reviewer: read-only pass over `dev` @ `85ecf30e`. Live reads: Chronos `transparenta_prod` (`ins.*`, `core.*`) and Phoenix dev `ins` DB, all `SELECT`/`EXPLAIN` under the sanctioned recipes. Nothing in the repo was modified except this file.

## Summary (5 lines)

1. **The Chronos dev canary is Phoenix-free for INS**: the overlay overrides the image command to `dist/redesign-api.js` (`k8s/overlays/chronos-dev/workload-patch.yaml:43-44`), and `buildRedesignApp` enables `ins-native` by default (`src/app/build-redesign-app.ts:259`). The shipped default image (`Dockerfile:102` → `dist/api.js`) still mounts the **legacy Phoenix INS module on `/api/v1/graphql`** via `makeInsInterimSurface` (`src/app/build-app.ts:1221-1224`) and hard-requires `INS_DATABASE_URL` (`src/infra/config/env.ts:38`, `src/app/build-plan.ts:146-150`). The client is already native-only (`sourcePins`, `geographicWitnesses`, `canonical_siruta_code`; 38 references to `/api/v1/graphql`), so any `api.js` deployment now serves an INS SDL the client cannot validate against (P1).
2. **Module shape**: `core/` + `shell/{repo,graphql,mcp,db,contributor}` with `makeInsNativeModule(deps)`; GraphQL serves exactly the 8 client roots; 4 MCP tools, read-only via the kernel's global annotation. **No REST** (`shell/rest` absent; issues register B14 "deferred"), which the binding contract requires (P2). No throws in core, no floats on values, no `JSON.parse`, no write SQL.
3. **Data parity**: Chronos `ins.*` is one publication (run 22915, 1,916/1,916 datasets on transform `bddc45cd…`, applied 2026-09-06); the POP107D admission pin (`revision 1051`, custody `429008f7…`) matches live. Phoenix dev was last synced 2026-02-05 and stops at year 2025; Chronos carries 2026 for POP107D and revised 2025 values (Cluj-Napoca 2025: Phoenix 325,353 vs Chronos 325,408) — lineage, not a bug. Row counts differ by design (Phoenix loads a bounded history: Cluj-Napoca POP107D 3,120 rows vs 10,920).
4. **Territory identity**: 42/42 counties resolve through the canonical-county alias join with zero forward/reverse conflicts; 3,181/3,183 LAU nodes are linked to `core.territories` (the two unlinked, 70049 CERNELE and 167589 GORANU, are the known A17 residual). Neither DB has sector nodes; Bucharest county `B`, municipality `179132` and the six sectors are distinct as documented. Sector admission rows exist for all 8 pinned years (48 rows, 8 distinct sources, all pass the canonical-sector predicate); 2021 and pre-2017 are absent by design; 2020 is admitted from the 2019 custody PDF (identical SHA). The `rowsSha256` recompute was not run (command denied) — unverified.
5. **Performance**: every modern-scope predicate filters `dataset_geo_tuples.territory_id` after a PK bitmap scan of the whole dataset's tuples (EXPLAIN: `Rows Removed by Filter: 3223` per territory per dataset); a `(dataset_code, territory_id)` index on the scrapper side is the single highest-leverage fix. Catalog reads re-validate publication custody over all 209k geo tuples per request (286 ms measured for `datasetsForTerritory`, Cluj-Napoca) with no cache (B14). Golden-master INS "pass" evidence is for the interim (Phoenix) surface only; no in-repo golden run has exercised the native slice against live data.
