## 1. Headline verdicts

1. **Chronos dev is Phoenix-free and matches its pin.** The pod runs
   `dist/redesign-api.js`; its secret carries only the serving-DB URL and Clerk keys;
   egress is default-deny to Chronos Postgres, Meili, OpenSearch and the dev user DB;
   the live image equals the overlay pin at HEAD and Argo is synced to `85ecf30e`.
   Every money path on that deployment uses one factor source, promoted set 2
   (digest matches the code pin). Verified by three agents and the lead.
2. **The hazard runs the other way: Phoenix dev embeds a stale kernel.** Phoenix dev
   (server image `b80c4778`, 2026-09-04, auto-synced manifests) serves
   `/api/v1/graphql` from `build-app.ts` with `REDESIGN_SURFACE_ENABLED=true`. On that
   surface `executionAnalytics` uses unpromoted factor set 1 with carry-forward,
   `budgetEntityRanking`/heatmaps/timeseries use an embedded JS-float table (2025 EUR
   5.05, GDP 1.88 T, 2026 estimates), and `entityAnalytics` does not exist yet
   (lead probe 2026-09-09). Prod exposes no kernel surface (`/api/v1/graphql` → 404),
   so nothing here is prod-facing today. **No P0.**
3. **One P1 money defect, upstream, server-visible (D/DP-01).** Chronos flags
   `is_yearly` per (entity, year, report type, main creditor), so an entity whose main
   creditor changed mid-year has two yearly rows and the annual MV sums both. Lead
   re-verified: entity 26429279 2024 detailed expense is 2.92 bn on Chronos vs
   2.05 bn on Phoenix; exposure is the disjoint-handover class only: 115 / 1 / 54
   scopes in 2023 / 2024 / 2025 (the other ~6,150 multi-creditor scopes per year are
   parallel reporting and sum correctly on both sides). The fix belongs to the
   scrapper fact rebuild (T104000 `is_year_end` flags are still unpopulated); the
   server cannot correct it from the annual MV.
4. **Scope gap vs doc 13.** `heatmapCountyData`, `heatmapUATData`,
   `commitmentsSummary/Aggregated/Analytics`, `entities`, `uats`, `datasets`,
   `staticChartAnalytics` are not on the kernel although doc 13 §2/§4 assign them to
   kernel modules (B/F1, T/T-09, N §Q5; lead probe confirms). 21 of 63 cutover cases
   are red by construction until this is ported or the doc is amended to "replaced by
   native roots + client migration".
5. **CI has been lying green.** Two different harnesses are involved. The nightly
   _snapshot_ golden master (12 hand-written specs against one legacy `/graphql`
   URL) targets a dev hostname with no ingress (`dev-api.` instead of `api-dev.`),
   so its Dev job has returned 404 on every run since 2026-03-07; its Prod job
   compares Phoenix prod against snapshots recorded before an entity-name casing
   change and reports 38 stale mismatches. Both jobs are `continue-on-error`, so
   the workflow shows success either way (T/T-01..03; lead verified the last run's
   job conclusions). Prod itself is not implicated: it has no kernel surface. The
   _cutover replay_ (63 client documents, legacy vs kernel) runs nowhere in CI,
   `tests/e2e` (51 files, the only real-Postgres proofs) never runs in CI, and
   CodeQL scans `main` only.
6. **Code quality of the new slices is high on the rules that matter.** Across all
   seven areas: no `throw` in `core/`, no float on money on the Chronos path,
   no raw `JSON.parse`, no write SQL against the serving DB, no cross-source
   internal imports, SDL byte-identity tests for the carried roots, and Decimal end
   to end. Privacy: the kernel identity hub, search, parliament votes, INS and the
   grouped budget roots gate `privacy_class` in SQL; five reads in legal, companies
   and the kernel territory repo do not (§2.1b), and the lead confirmed every one
   of those tables holds zero non-public rows today, so they are latent gaps, not
   exposures. The gates pass on this tree (typecheck, lint 0 warnings,
   deps:check; 5,719 unit/integration tests pass, one known load flake).
